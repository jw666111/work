## 一、产品定位

**Usher Cloud** 是面向非研发用户的前端页面及物料自助生产平台，用户无需理解 Git、代码仓库、分支、本地环境，通过自然语言描述需求即可获得可用的设计产出。

产品核心差异化：

- **零配置、浏览器访问**：服务端执行，用户只需浏览器，无需本地环境
- **结构化输入 + AI 生成**：通过表单卡片和澄清对话，让非专业用户也能准确表达需求
- **所见即所得的二次编辑**：生成结果可精确调整文字/颜色/布局，操作难度对标"改 PPT"而非"用 Figma"
- **场景化交付**：不同场景对应不同的交付链路——官网活动页走 Code Review、Banner 直接发布、印刷物料走文件导出

### 与现有 Usher 的关系

| 产品 | 主要用户 | 产品形态 |
| ----------- | --------------- | ---------------- |
| 现有 Usher | 专业研发 | 本地开发工具与 Agent |
| Usher Cloud | 非研发用户为主，也支持研发协同 | 浏览器访问、服务端执行、固定场景 |

Usher Cloud 是现有 Usher 能力的云端托管分支，不替代现有 Usher，底层复用部分能力，但产品入口、交互方式和目标用户独立设计。

### 非目标（管理预期）

- 不追求替代专业设计师做品牌级视觉创意（大型 campaign KV、复杂海报）
- 不追求 Figma 级别的自由创作能力
- 不覆盖复杂业务逻辑开发（提示超出范围）
- 一期不接入海外官网、SurferCloud、其他控制台渠道

## 二、目标用户与典型痛点

### 目标用户

| 用户角色 | 说明 | 典型场景 |
| --------- | ---------------- | --------------------- |
| 市场部/品牌部同事 | 非设计背景，高频产出线下物料 | 展会易拉宝、宣传页、活动海报 |
| 运营/活动运营 | 需要快速上线线上活动页 | 促销活动、新品发布 |
| 市场推广 | 需要制作和更新首页 Banner | 周年庆、大促、品牌宣传 |
| 研发协同人员 | 需要与研发协作完成页面开发 | 配合提交 Code Review、确认发布 |

### 典型痛点

- **工具门槛高**：Figma/PS/AI 学习成本高，非设计背景同事做不出像样排版
- **设计师资源稀缺、排期慢**：一个小需求也要排期 1-2 天，而活动经常"今天要明天用"
- **临时性/高频/低复杂度需求被长期忽视**：量大但单个价值低，长期被 PPT 糊弄
- **反复修改成本高**：文案改一版、日期改一版，找设计师来回沟通成本高
- **活动页上线流程长**：需要对接研发、走排期、测试、发布，一个简单的活动页也要几天

### 核心价值主张

> **"输入一段话，30 秒内拿到一版可用的设计/页面"**
> 把"表达需求"到"看到结果"的距离缩短到自然语言描述。
> 区别于纯 AI 出图工具（不可编辑）和专业设计软件（学习成本高）。

### 6.1 首页/工作台

#### 6.1.1 界面布局

页面采用**左侧窄导航侧栏 + 右侧主内容区**的双栏布局：

```
┌──────────┬──────────────────────────────────────┐
│ 导航侧栏  │  主内容区                             │
│ (200px)  │                                      │
│          │  ┌────────────────────────────────┐   │
│  🏠 首页  │  │  Usher Cloud                  │   │
│  📄 活动页 │  │  描述你的需求…                  │   │
│  🖼 Banner │  │  [输入框...]      [开始生成]    │   │
│  🎨 设计工具 │  └────────────────────────────────┘   │
│          │  ┌──────┐ ┌──────┐ ┌──────┐      │
│  📋 任务   │  │活动页 │ │Banner │ │设计工具│      │
│          │  │ 卡片  │ │ 卡片  │ │ 卡片  │      │
│  👤 用户   │  └──────┘ └──────┘ └──────┘      │
│          │  ┌────────────────────────────────┐   │
│          │  │  最近任务                        │   │
│          │  │  [表格列表...]                  │   │
│          │  └────────────────────────────────┘   │
└──────────┴──────────────────────────────────────┘
```

- 导航侧栏固定宽度 200px，深色背景（#1a1a2e），白色文字图标，全局所有页面保持一致
- 主内容区浅色背景（#f5f6fa），白色卡片区块，圆角阴影

#### 6.1.2 界面元素与交互说明

##### A. 左侧导航侧栏

| 元素 | 说明 | 交互 |
|------|------|------|
| 应用Logo区域 | 顶部 "Usher Cloud" 品牌文字或图标 | 始终展示，点击回到首页 |
| 导航项（第1组场景） | 首页(🏠)、活动页(📄)、Banner(🖼️)、设计工具(🎨) | 默认"首页"高亮；点击切换页面，选中项白色高亮文字+背景色块 |
| 导航项（第2组工具） | 我的任务(📋) | 点击进入任务列表 |
| 导航项（P2预留） | 页面快改(置灰)、控制台原型稿(置灰) | 显示锁定图标+"/敬请期待"；置灰不可点击，hover 显示 Tooltip "即将上线" |
| 用户区域 | 底部用户头像（首字母/默认头像）+ 用户名 | 点击展开下拉菜单（设置/退出） |

- **选中态**：选中项背景色块（白色半透明底），图标+文字白色
- **悬停态**：非选中项 hover 时文字变浅白色，背景轻微变亮
- **展开/收起**：一期固定宽度，不支持折叠

##### B. 欢迎区 / Brief 输入框

| 元素 | 说明 |
|------|------|
| 主标题 | "Usher Cloud"，大号加粗 |
| 副标题 | "描述你的需求，30秒获得一版可用的设计"，灰色小字 |
| 文本输入框 | 单行/多行自适应输入框，placeholder="描述你想要创建的页面或物料……" |
| "开始生成" 按钮 | 蓝色主按钮 |

**交互流程**：

1. 默认态：显示主标题 + 副标题 + 空输入框 + 置灰"开始生成"按钮
2. 输入态：用户输入文字后，"开始生成"按钮变为可点击（蓝色高亮）
3. 输入超过 3 个字时，按钮下方出现智能场景识别提示："检测到您可能想创建【活动页面】，是否直接进入场景？" 带"是"和"取消"
4. 场景识别匹配规则：
   - 包含"活动/促销/套餐/首发/新品" → 匹配"官网活动页"
   - 包含"Banner/横幅/首页/大促/周年" → 匹配"官网首页 Banner"
   - 包含"展板/易拉宝/宣传页/DM/印刷/物料" → 匹配"市场部设计工具"
   - 无法匹配 → 提示"请从下方场景卡片进入或补充更多描述"
5. 点击"开始生成"：若输入框为空，按钮置灰不可点击；若有文字但无法识别场景，toast 提示"请从下方场景卡片选择"
6. 回车键（Enter）在输入框聚焦时可触发"开始生成"
7. 输入框支持粘贴富文本，自动转为纯文本

##### C. 场景卡片区

三张卡片水平等间距排列，每张宽度均分：

| 卡片 | 图标 | 标题 | 描述 | 交付标签 |
|------|------|------|------|---------|
| 官网活动页 | 📄 | 官网活动页 | 创建促销活动、新品发布页面 | `Code Review`（蓝色标签） |
| 官网首页 Banner | 🖼️ | 官网首页 Banner | 制作官网顶部 Banner 并直接发布 | `自动发布`（绿色标签） |
| 市场部设计工具 | 🎨 | 市场部设计工具 | 制作展板/易拉宝/宣传页等印刷物料 | `导出文件`（橙色标签） |

**交互说明**：

| 状态 | 说明 |
|------|------|
| **默认态** | 白色卡片，圆角 12px，阴影 light，卡片内图标+标题+描述+标签 |
| **悬停态** | 卡片上浮阴影加重，整体轻微上移 2px 动效，描述文字颜色加深 |
| **点击态** | 点击后跳转到对应场景创建页面，浏览器路由变更 |
| **点击交互** | 也支持点击卡片任意区域跳转（整个卡片是热区），不单独设"进入"按钮 |

**P2场景卡片**（不展示或置灰展示，位于第三张卡片右侧或下方）：
- 页面快改 🚧 "即将上线" 置灰
- 控制台原型稿 🚧 "即将上线" 置灰

##### D. 最近任务区

| 元素 | 说明 |
|------|------|
| 区块标题 | "最近任务" + "查看全部"链接（点击进入完整任务列表） |
| 列表 | 表格展示最近 5 条任务记录 |
| 加载更多 | 尾部"加载更多"按钮，每次 +5 |

**字段定义**：

| 列 | 类型 | 内容说明 |
|-----|------|---------|
| 任务名称 | 文本 | 用户创建时自动命名的标题（如"双11活动页"） |
| 类型 | 标签 | 官网活动页/首页 Banner/设计工具，带对应场景图标 |
| 状态 | 状态标签 | 处理中（蓝色）/ 已完成（绿色）/ 失败（红色） |
| 创建时间 | 相对时间 | "3 分钟前""昨天 14:30""2026-07-28" |
| 操作 | 按钮 | 处理中→"继续编辑" / 已完成→"查看详情" / 失败→"重新生成" |

**绑定交互**：

- 处理中的任务有实时状态轮询（每 10 秒），状态变更时自动更新
- 完成或失败的 toast 通知
- 点击行任意区域进入对应编辑页面

#### 6.1.3 主要操作流程

```
用户进入首页
  │
  ├─ 方式A：通过 Brief 输入框
  │    输入需求描述 → 识别场景 → 点击"开始生成"
  │    → 跳转到对应场景页面（输入内容自动带入）
  │
  ├─ 方式B：通过场景卡片
  │    点击场景卡片 → 跳转到对应场景创建页面
  │
  └─ 方式C：通过我的任务
      点击任务行 → 进入对应编辑/查看页面
```

#### 6.1.4 状态说明

| 状态 | 触发条件 | 界面表现 |
|------|---------|---------|
| **加载态** | 页面首次加载 | 骨架屏（导航侧栏灰色块 + 欢迎区灰色块 + 三张卡片灰色块） |
| **空态（无任务）** | 新用户尚无任务记录 | 任务区显示"还没有任务，开始创建第一个吧"空状态插图，同时指引"试试从上方场景卡片开始" |
| **场景识别失败** | 输入内容无法匹配任何场景 | 按钮下方红色提示"暂未识别到场景，请从下方卡片选择" |
| **任务处理中** | 后台正在生成 | 任务列表该行显示旋转加载图标，"处理中"标签蓝色 |
| **任务完成** | 生成成功 | 任务状态变"已完成"标签绿色，浏览器通知(如有权限) |
| **任务失败** | 生成异常/超时 | 状态变"失败"标签红色，操作列出现"重新生成"按钮 |
| **网络断开** | 网络异常 | 页面顶部全局提示条"网络已断开，请检查连接"，重连后自动消失 |

#### 6.2.2 界面元素与交互说明（区块级）

##### 区块1：套餐配置

| 元素 | 说明 |
|------|------|
| 卡片标题 | "套餐配置" + 右上角"导入 Excel"链接 |
| 配置表格 | 多行可编辑表格，每行包含 14 个字段（见下方字段表） |

## 七、通用产品交互原则

以下原则贯穿所有一期场景，确保体验一致性：

### 7.1 输入范式：结构化输入 + 对话式澄清

所有场景采用统一的输入模式：先通过结构化表单卡片收集关键信息（降低用户输入门槛），提交后 AI 主动识别缺失/模糊信息，通过聊天式追问逐项澄清，全部确认后方可进入生成阶段。这一模式区别于"一句话生成"类工具，用信息完整度换取生成成功率。

### 7.2 生成策略：场景决定方案数量

| 场景 | 生成策略 | 原因 |
| ------ | ----- | -------------------------------- |
| 活动页 | 单方案生成 | 有套餐数据和模板约束，生成确定性高 |
| Banner | 多候选生成 | Banner 对视觉风格/创意的选择空间大，多候选让用户有选择权 |
| 设计工具 | 单方案生成 | 有结构化输入+澄清确认保证信息完整性，信息充分则一次生成即可满足 |

### 7.3 编辑器：所见即所得 + 对话式调整

所有场景生成后进入所见即所得编辑器，用户可通过以下两种方式调整：

1. **对话式调整**：在 AI 对话区输入自然语言指令（"标题再大一点""背景换成蓝色"），AI 执行修改后刷新预览
2. **直接操作**（设计工具场景）：在画布上选中图层，通过浮动工具条调整属性（字号/颜色/位置等）

### 7.4 撤销/重做

所有编辑器必须支持基础撤销/重做，防止误操作导致用户信任流失。

### 7.5 生成等待态

生成过程中需同时提供两处等待反馈：对话区内 AI 消息给出文字进度说明，预览区出现骨架屏占位，让用户清楚结果即将出现的位置。

### 7.6 Toast 提示规范

操作反馈统一采用顶部居中 toast，持续 3 秒后自动消失。错误类 toast 需要用户手动关闭。

| 类型 | 颜色 | 图标 |
|------|------|------|
| 成功 | 绿色 | ✅ |
| 失败/错误 | 红色 | ❌ |
| 警告 | 橙色 | ⚠️ |
| 信息 | 蓝色 | ℹ️ |

### 7.7 空状态/引导设计

所有页面的空状态必须提供"下一步操作指引"，不允许出现空白页：

- 首页：无任务 → 引导选择场景卡片
- 创建页：未输入 → placeholder 引导
- 编辑器：无选中 → 提示"点击画布中的元素开始编辑"
- 版本列表：无历史 → "还没有发布记录"

## 八、优先级 P2（本期不涵盖）

以下两个场景经过评估，一期不做开发，优先级改为 P2，保留入口（置灰状态或隐藏），待一期验证通过后再启动。

### 8.1 页面快改（P2）

**定位**：用户输入页面 URL、选中页面元素，AI 直接修改线上页面代码，提交 Code Review。

**推迟原因**：

- 该场景需要加载真实线上页面、实现元素选择器、实时预览修改效果，技术复杂度较高
- 依赖"所见即所得元素选择"交互能力，与本期三个场景的"从零生成"模式差异大
- 真实页面修改的风险控制要求更高（误改、样式破坏等），需要更完善的兜底机制

**预计涵盖范围**：

- 官网（国内站）与控制台（主渠道）两个站点
- 页面 URL 输入 → 加载真实页面 → 鼠标选择元素 → 发送到对话 → AI 修改 → 实时预览 → 提交 Code Review

### 8.2 控制台原型稿（P2）

**定位**：用户通过自然语言生成控制台界面原型，支持标注、分享链接，供产品/设计/研发协作。

**推迟原因**：

- 原型场景的核心价值是"快速沟通对齐"，与一期聚焦的"生产可交付物"方向不同
- 控制台原型与真实控制台项目的衔接（如何从原型→代码实现）需要额外的整体方案设计
- 原型测试建议放在产品迭代验证阶段，结合真实用户反馈设计更精准的交互

**预计涵盖范围**：

- 历史原型列表、新建原型、AI 输入描述生成原型
- 所见即所得修改、在线标注、自动保存、分享链接

## 十、风险与挑战

- **AI 生成质量不稳定**：LLM 对空间关系、视觉平衡、留白美学的判断能力有限，需依赖模板约束 + 规则引擎校验保障基础质量，不能假设一次到位
- **用户预期管理**：不能引导用户预期"AI 一键生成专业级作品"，应定位为"AI 帮你快速起草 + 你做最终把关式微调"
- **性能与延迟**：AI 生成 + 澄清确认往返 + 可能的文生图调用，端到端时延可能达十几秒到几十秒，需设计等待态体验（骨架屏、进度提示）缓解焦虑
- **图片素材版权**：图库素材授权范围、AI 生成图片可商用性，需提前法务/采购确认
- **三个场景的编辑器复杂度不同**：Banner 场景编辑器相对轻量，活动页需要处理套餐数据联动，设计工具需要完整的画布/图层/浮动工具条——需要判断是否共用同一套编辑器底层，还是各场景独立实现
- **印刷交付的专业门槛**：市场部同事不熟悉"出血""色彩空间""DPI"等印刷概念，需设计"智能预设+大白话说明"的交互，避免用户因不懂参数选错导致印厂返工

## 十一、待确认与补充项

> 以下为合并两个文档后发现的需要进一步明确或补充的关键问题，标注 ⚠️ 的为建议在一期启动前优先确认。

### 🔴 产品定位相关问题

- **⚠️ 【定位确认】市场部 AI 设计工具作为 Usher Cloud 的一个子场景，还是独立产品线？** 当前合并方案将其作为 Usher Cloud 的第三个场景入口。需要确认团队是否认同这一产品归属关系，或者更倾向于两个产品独立运营（Usher Cloud 仅做线上场景，设计工具另起项目）。
- **⚠️ 【目标用户统一】三类场景的目标用户画像差异较大**：活动页面向运营同学、Banner 面向市场推广、设计工具面向市场部同事。需要确认是否需要在产品内做用户角色分流（不同角色看到不同默认场景），还是保持统一的入口页面让用户自行选择。
- **【非目标补充】设计工具是否需要覆盖"内部通知/公告"类物料？** 市场部 PRD 中提到了"内部通知"但未在 MVP 功能中体现，需确认是否应明确归入非目标或二期。

### 🟠 场景边界问题

- **⚠️ 【活动页与设计工具的边界】** 官网活动页最终产出是提交 Code Review 的页面代码；市场部设计工具产出是 PNG/PDF 文件。两者的交付链路完全不同。是否有中间态场景（如"活动宣传海报"既需要在官网展示也需要印刷）需要同时在两个场景中满足？
- **【Banner 的多候选生成策略是否适用于其他场景？】** 当前方案中 Banner 是多候选、活动页和设计工具是单方案。这个差异化策略是否经过用户验证？如果一期反馈发现用户在其他场景也想要多候选选择，是否需要预留扩展空间？
- **【套餐配置的灵活度】** 活动套餐配置表中的"促销策略"字段比较宽泛，是否应进一步拆分为更具体的字段（如满减/折扣/赠品等类型）还是保持文本输入？

### 🟡 交互与体验问题

- **⚠️ 【澄清确认引擎的统一性】市场部设计工具采用了完整的"澄清确认对话"机制（信息补全后再生成）。这个机制是否也应该应用于活动页和 Banner 场景？** 如果应用，活动页/Banner 的"澄清"要问什么问题需要定义。
- **【设计工具的画布编辑器 vs 活动页/Banner 的预览编辑器】** 是否存在编辑器层面复用的可能？还是三类场景各自使用独立的编辑方案？这直接影响技术架构和用户体验一致性。
- **【设计工具的"浮动工具条"交互是否适合非设计用户？】** 原有 PRD 的设计是"不设常驻图层面板，选中图层时浮现浮动工具条"。对于完全非设计背景的用户，浮动工具条可能不够直观。是否需要保留一个简化的常驻属性侧栏（类似 Canva 的极简模式）作为备选？

### 🟢 流程与交付问题

- **⚠️ 【设计工具的导出质量确认】市场部设计工具的 PDF 导出是否确实需要印刷级精度（出血线、裁切线、300dpi+）？** 如果只是发朋友圈/公众号配图，前端截图方案已够用，印刷级导出会显著增加服务端渲染的开发成本。建议与市场部确认印刷交付的真实比例。
- **【Banner 自动发布的风险管控】** Banner 自动发布到官网场景涉及线上页面直接变更，是否需要审批环节？一期方案是"用户确认即发布"，是否需要增加"二次确认"或"预览链接审核"的兜底？
- **【活动页的套餐数据写入时机】** 套餐配置数据是先写入数据库再生成页面，还是先生成页面预览、用户确认后再写入？如果生成后用户修改套餐配置，数据的同步策略是什么？
- **【权限控制的颗粒度】** 哪些用户可以访问哪些场景？市场部同事是否应该能看到活动页/Banner 入口？活动页提交 Code Review 是否需要指定 reviewer？这些权限规则需要明确。

### 🔵 优先级与范围问题

- **⚠️ 【P2 场景的一期预处理】** 页面快改和原型稿虽然本期不做，是否需要在一期架构层面预留入口和扩展点（如首页场景卡片占位），还是二期再整体加入？这影响前端框架设计。
- **【模板库的初始投入】** 活动页模板、Banner 模板、设计工具模板——三类模板是分别建设还是共享部分模板资产？一期启动时模板的初始数量和质量标准是什么？
- **【品牌规范锁定列为二期的确认】** 市场部 PRD 将品牌规范锁定放在二期。但活动页和 Banner 场景同样面临"生成结果是否符合品牌调性"的问题。是否应该在一期就引入基础的品牌约束（如限定字体/主色调），而非留给二期？
